# WS1 Terminal E2EE — Implementation & Trust Boundary

**Date:** 2026-10-07
**Layer:** 1 (WS1) of Phase 5's three-layer design — terminal data channel only
**Scope:** Application-layer confidentiality of a single terminal session's data channel, negotiated between two peers that have already authenticated each other through WS2.

> **Superseded in part (2026-10-08).** Week 16 shipped the Rust agent peer, so the "agent has no
> producer yet / lands Week 16" statements below describe the Week 15 state only. See the Week 16
> note [docs/security/2026-10-08-ws1-e2ee-rust.md](./2026-10-08-ws1-e2ee-rust.md).

## Deliverables

This document covers the Week 15 (WS1 part 1) deliverables — browser side only. Each fails closed when its gate applies:

1. **Key schedule (H7/C1/C4).** The browser generates an ECDH P-256 keypair on first use and persists it in IndexedDB (`packages/crypto/src/index.ts`, store `keys`). A per-session symmetric key is derived by `EncryptionManager.derive` (`packages/crypto/src/encrypt.ts`): ECDH `deriveBits` → HKDF-SHA256 → AES-GCM-256. The raw shared secret is never used directly; HKDF binds the derived key to a session (`salt`) and a purpose (`info`).

   - `info` = `ponter-ws1-terminal-v1` (`WS1_TERMINAL_INFO`, `packages/shared/src/types/e2ee.ts`).
   - `salt` = the WebRTC session id, as UTF-8 bytes (`buildSessionKey`, `packages/crypto/src/session-key.ts`).
   - `WS1_KEY_VERSION` = `ponter-ws1-v1`; the signed binding string is
     `ponter-ws1-v1\necdhPublicKey=<spki-base64>` (`canonicalKeyBinding`).

2. **Ciphertext framing.** `EncryptionManager.encrypt` produces `[12-byte IV][AES-GCM ciphertext ‖ 16-byte tag]` (`IV_BYTES = 12`). `decrypt` throws on a frame shorter than 12 bytes or on a failed authentication tag, so a truncated or tampered payload is rejected before any plaintext is released.

3. **Negotiation frames (H7).** Two new terminal-channel frames, carried as terminal data frames whose `payload.data` holds the binary blob:
   - `terminal-e2ee-hello` — the offerer proposes its ECDH public key and an Ed25519 signature over the canonical binding.
   - `terminal-e2ee-ack` — the answerer returns its own key binding after verifying the offerer's.

4. **Key persistence (H4).** The browser keeps the ECDH private key across sessions: `logout()` in `apps/web/src/stores/auth.ts` no longer deletes it, so the same long-lived identity keypair is reused on the next login. The signing key (WS2) remains on separate footing in the `signing-keys` store.

## Trust boundary

The ECDH key a peer advertises on the data channel is authenticated only by the WS2 Ed25519 identity. `buildSessionKey` (`packages/crypto/src/session-key.ts`) verifies the peer's Ed25519 signature over `canonicalKeyBinding(ecdhPublicKey)` against the peer signing key learned from `GET /api/agents` (WS2). Only after that verification succeeds does it derive a key. A signature that does not verify throws and the session stays plaintext — no half-verified key is ever adopted.

**Residual risk — unchanged from WS2.** The trust boundary does **not** defend against a signaling server that substitutes the identity keys themselves (TOFU on the peer signing key). If the server replaced a user's `signingPublicKey` in the DB with an attacker-controlled key, the agent would accept the attacker's binding. That is the documented Phase 5 boundary (spec §8): H6 is closed with a keypair, not a full PKI; server-side key attestation / certificate provisioning is out of scope for Phase 5.

## Fail-closed table

| # | Point | When the check fails | Effect on the terminal session |
|---|-------|----------------------|-------------------------------|
| 1 | `buildSessionKey`: peer signature does not verify against the WS2 signing key | Negotiation aborts before any key is accepted | Session stays on the existing (plaintext) path; no data is encrypted and no tampered key is adopted |
| 2 | `buildSessionKey`: ECDH public key is malformed | `importPublicKeySpki` rejects it | Negotiation aborts; session stays plaintext |
| 3 | `EncryptionManager.decrypt`: frame is shorter than 12 bytes | IV cannot be parsed | Decrypt throws; the frame is surfaced as an error, never rendered as plaintext |
| 4 | `EncryptionManager.decrypt`: AES-GCM tag fails | Integrity check fails | Decrypt throws; corrupted or tampered ciphertext is surfaced as an error, never silently truncated |
| 5 | Peer omits `capabilities: ["e2ee"]` (or the answer carries no capability) | Negotiator sees no capability | `TerminalE2ee.isActive()` stays false; `encrypt`/`decrypt` are identity (plaintext passthrough) |

Rows 1–2 are the browser-side key-adoption gate, enforced in `buildSessionKey` before `EncryptionManager.derive` returns. Row 3–4 are the ciphertext-integrity gate, enforced inside `EncryptionManager.decrypt`. Row 5 is capability-driven negotiation: a peer that does not negotiate keeps the plaintext path.

## What WS1 part 1 does NOT do

This week delivers the **browser side only**. The Rust agent does not yet advertise or consume these frames, so terminal data on the live agent is **not** confidential this week.

- The browser-side `EncryptionManager`, `buildSessionKey`, and `TerminalE2ee` negotiation driver exist (`packages/crypto`, `packages/terminal-core/src/e2ee.ts`), but the agent has no corresponding producer of the `terminal-e2ee-hello`/`-ack` frames yet. A terminal session against the current agent therefore runs on its existing plaintext path.
- The `capabilities?: string[]` field added to `SignalAnswer` (`packages/shared/src/types/signaling.ts`) is **not read** this week. The server relay's `answer` branch (`apps/server/src/routes/ws.ts`, `parseSignalMessage`) carries only `sessionId`/`sdp`/`approved`/`proof`, and the browser parser (`packages/webrtc-core/src/transport.ts`, `parseSignalItem`, `answer` case) has no `capabilities` field — so an agent advertising `e2ee` in its answer cannot be seen by the browser. This is carry-forward (Week 16), not a defect fixed here.
- No Rust-side crypto this week: `git diff main..HEAD -- apps/agent/` is empty (layer-order gate). The Rust `EncryptionManager` (via `ring`), consuming the same `e2ee-vectors.json`, lands Week 16 — see the cross-language E2E gate G3 in the Phase 5 plan.
- Desktop-input encryption is out of scope this week.
- File transfer stays out of application-layer scope (spec §4.3): application-layer key negotiation is terminal-data only; file payloads are still confined to the existing DTLS transport protections and the Phase 4 file-transfer ADRs.
