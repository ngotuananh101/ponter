# WS1 Terminal E2EE — Rust Agent Peer and Cross-Language Proof

**Date:** 2026-10-08
**Scope:** Shipped WS1 terminal E2EE in Week 16 — the Rust agent-side crypto peer and the browser-side negotiation wiring — the shared `e2ee-vectors.json` consumed by both language test suites, the negotiated capability path (`e2ee` on the answerer), the fail-closed behavior, the token-storage decision, the cross-language E2E gate G3 that proves the two-way round trip, and the scope boundary for data that is not confidentiality-protected.

## Deliverables

This document covers the Week 16 (WS1 part 2) Rust-side shipment: a Rust peer that runs the same key schedule as the browser so a terminal data channel carries confidential data end to end between the browser and a live agent.

1. **Rust `EncryptionManager` over `ring`** (`apps/agent/src/e2ee.rs`): ECDH P-256 → HKDF-SHA256 → AES-GCM-256, the same key schedule the browser uses (`packages/crypto/src/encrypt.ts`, `packages/crypto/src/session-key.ts`).

2. **Byte-identical constants:**
   - `IV_BYTES = 12`, `TAG_BYTES = 16` (`apps/agent/src/e2ee.rs`).
   - `WS1_KEY_VERSION = "ponter-ws1-v1"` and `WS1_TERMINAL_INFO = "ponter-ws1-terminal-v1"`, matching `packages/shared/src/types/e2ee.ts`.
   - The canonical binding string is `canonical_key_binding(spki) = "{WS1_KEY_VERSION}\necdhPublicKey={spki-base64}"` (the `WS1_KEY_VERSION` constant; the browser's `canonicalKeyBinding` in `packages/shared/src/types/e2ee.ts`). The browser signs and checks this exact string, and the agent both verify it and sign its own copy in `accept_hello`.

3. **P-256 SPKI interop.** `P256_SPKI_PREFIX` (a 26-byte DER prefix in `apps/agent/src/e2ee.rs`) matches the browser's `exportPublicKeySpki` output, so an SPKI base64 produced by either side decodes on the other. `spki_from_raw_point` encodes a 65-byte uncompressed point; `raw_point_from_spki_b64` decodes it back and returns `MalformedFrame` for a non-uncompressed point. The Rust test `p256_public_point_spki_matches_js_export` asserts the round-trip and the fixed base64 value.

4. **Ciphertext framing.** Every frame is `[12-byte IV][AES-GCM ciphertext ‖ 16-byte tag]`, with a fresh random IV per frame (`SystemRandom`). `decrypt` rejects any frame whose length is `<= IV_BYTES + TAG_BYTES` (i.e. one with no room for a tag) before touching the nonce, and returns `E2eeError::Crypto` on a tag failure.

5. **Shared test vectors.** Both suites consume the same file — `packages/crypto/test/vectors/e2ee-vectors.json`. The Vitest suite (`packages/crypto/test/encrypt.test.ts`) and the Rust tests (path via `concat!(env!("CARGO_MANIFEST_DIR"), "/../../packages/crypto/test/vectors/e2ee-vectors.json")` in `apps/agent/src/e2ee.rs`) all read this file. The Rust tests assert:
   - HKDF-SHA256 against the RFC 5869 A.1 known-answer vector (`hkdf_matches_rfc5869_a1_vector`).
   - AES-256-GCM known-answer vector, including the framed decrypt round-trip (`aes_gcm_matches_kat_vector`).
   - The P-256 SPKI export matches the JS export byte-for-byte (`p256_public_point_spki_matches_js_export`).
   - ECDH agreement between two ephemeral keys (`ecdh_two_ephemeral_keys_agree`).
   - `EncryptionManager` encrypt→decrypt round-trip and reject-on-tamper (`encryption_manager_round_trips_and_rejects_tamper`).
   - `accept_hello` round-trip, including the browser-side re-derivation check (`accept_hello_derives_and_round_trips`).
   - A mis-signed hello is rejected with `BindingNotVerified` (`a_mis_signed_hello_is_rejected_and_yields_no_session`).

### Browser peer (WS1 part 2 client wiring)

The browser drives negotiation from `TerminalClient` (`packages/terminal-core/src/client.ts`). `createSession()` sends `terminal-create` (always plaintext) and, when an `E2eeContext` is present, enqueues the `terminal-e2ee-hello` on the same ordered `sendChain` used for terminal-data (T5-C). `negotiate(terminalId)` is public and idempotency-safe via two guards: `e2ee.isActive()` and a per-terminal `negotiatedTerminals` set, covering the in-flight window before the ack lands (`packages/terminal-core/src/client.ts` lines ~48–163).

The never-render-ciphertext invariant (T5-R1) lives in `handleMessage` (`packages/terminal-core/src/client.ts` ~line 271). When an `E2eeContext` is present, the entire `terminal-data` handling is enqueued on `receiveChain`, so the `isActive()` decision runs strictly after any already-queued ack callback (which performs the async key derivation). A ciphertext frame arriving while the ack's derivation is in flight must not take the plaintext branch. When `e2ee` is absent, the synchronous plaintext path is byte-identical to before. `terminal-e2ee-ack` is handled on `receiveChain`; the hello is answerer-side and ignored — the browser is always the offerer.

Capability plumbing: `createAnswerSignal(...)` gains a `capabilities` param (`packages/webrtc-core/src/signal-handler.ts`); `PeerConnection.getRemoteCapabilities()` records the remote answer's capabilities (`packages/webrtc-core/src/connection.ts` ~line 110); the polling transport parser preserves `capabilities` in its `answer` case (`packages/webrtc-core/src/transport.ts` ~line 277).

Key persistence: `savePublicKey`/`loadPublicKey` in `packages/crypto/src/index.ts` store the ECDH public key under the `"${userId}:pub"` suffix — not the bare `userId`, which would overwrite the private key. The register flow persists it in `apps/web/src/stores/auth.ts` (around line 232).

Store wiring (fail-closed): `buildE2eeContext()` in `apps/web/src/stores/terminal.ts` returns `null` unless the user's ECDH private + public keys, the signing key, and the agent's signing public key are all present. The terminal offer carries `capabilities: ['terminal','e2ee']` only when a context exists; `TerminalClient` receives the `TerminalE2ee` driver only when `peer.getRemoteCapabilities().includes('e2ee')`. Otherwise the client is constructed with no third argument — plaintext parity.

Desktop: `DesktopClient` takes an optional `DesktopE2eeDriver` (a structural subset of `TerminalE2ee`, so `desktop-core` does not import `terminal-core` — `packages/desktop-core/src/types.ts`). It sends `desktop-e2ee-hello` once the control channel opens (idempotent via `e2eeNegotiated`), installs the key on `desktop-e2ee-ack`, and encrypts only `desktop-input` frames when active; all other control frames stay plaintext (`packages/desktop-core/src/client.ts` ~lines 250–502).

## Cross-language E2E gate G3

The cross-language round trip is proven by `packages/webrtc-core/test/e2e/terminal-e2ee.e2e.test.ts` (2/2 pass on Linux under `describe.skipIf(!isLinux)`).

- **Test (a) "negotiates E2EE and round-trips terminal bytes across the language boundary":** the Rust agent decrypts a browser-encrypted payload and the browser decrypts the agent's encrypted output. The browser is always the offerer; `openE2eeTerminalPeer` builds the offer with `capabilities: ['terminal', 'e2ee']` and wires `TerminalE2ee` into `TerminalClient` (`packages/webrtc-core/test/e2e/harness.ts`). `negotiateTerminalE2ee` calls `createSession()` — which enqueues the hello on the sendChain (T5-C) — then polls `e2ee.isActive()` until the agent's `terminal-e2ee-ack` installs the session key. The test drives the encrypting path via `session.write(...)` through `TerminalClient.sendInput`; it reads the decrypted output via `session.onData`, never the raw `frames` array.
- **Test (b) "a legacy agent (no e2ee capability) yields a plaintext, byte-identical terminal":** the offer carries no `e2ee`, so `peer.getRemoteCapabilities()` does not contain `e2ee`, and the plaintext round trip is verified via `sendKeystrokes`.

Harness additions: `seedSignedTerminal` now returns `agentSigningPublicKey` (the agent's WS2 Ed25519 key fetched from `GET /api/agents`) alongside the pre-existing fields (`packages/webrtc-core/test/e2e/harness.ts`). `openE2eeTerminalPeer` constructs `TerminalE2ee` from the `E2eeContext` and passes it to `TerminalClient`, so negotiation is self-driven by `createSession()`.

Ruling T7-R1: `terminal-core` is imported by relative path (`../../../terminal-core/src/client`, `../../../terminal-core/src/e2ee`) in the harness — never as a manifest dependency. `@ponter/terminal-core` already depends on `@ponter/webrtc-core`; adding the reverse edge would make turbo's type-check graph cyclic and hard-fail. Relative imports are invisible to turbo's manifest-based graph.

## Test coverage and its limits

- **Store E2EE tests** (`apps/web/src/__tests__/terminal-store.test.ts`, describes `useTerminalStore E2EE negotiation` and `useTerminalStore desktop E2EE negotiation`) **mock** `@ponter/terminal-core` and `@ponter/crypto`. They are **wiring-only**: they assert that the store selects the right capabilities and passes an `E2eeContext` / driver, not that the cryptography works. A mock-driven `isActive()` returning `true` does not exercise a real `EncryptionManager`.
- **Cryptographic correctness** is covered by dedicated suites:
  - `packages/terminal-core/test/e2ee.test.ts` — negotiation, the never-render-ciphertext ordering guard (T5-R1), and the receive-path gate on `receiveChain`.
  - `packages/desktop-core/test/client.test.ts` — plaintext parity, dormant-driver byte-identity, idempotent hello, send-chain ordering, and failure isolation.
  - `packages/crypto/test/crypto.test.ts` — public-key round-trip and the `:pub` suffix isolation (the bare `userId` key is not clobbered).
  - `packages/crypto/test/encrypt.test.ts` and `packages/crypto/test/session-key.test.ts` — `EncryptionManager` round-trip, reject-on-tamper, and `buildSessionKey`'s verify-before-derive gate.
  - The cross-language **gate G3** E2E (`terminal-e2ee.e2e.test.ts`) against the real Rust agent — the only test that exercises the shipped Rust `accept_hello` + `pump_frame` activation barrier end to end.

## Negotiation flow

The agent never starts this negotiation; it only echoes a capability the offer proposed. The gating constant is `E2EE_CAPABILITY = "e2ee"` (`apps/agent/src/rtc.rs`).

1. The browser's offer carries `capabilities: [..., "e2ee"]` — only when it holds an ECDH key (`packages/shared/src/types/e2ee.ts`).
2. The agent answers with `capabilities: ["e2ee"]` (echoed), via `send_desktop_answer` / the terminal `answer_offer` path. The field on the wire is `SignalAnswer.capabilities` (`apps/agent/src/signal.rs`), with `#[serde(default, skip_serializing_if = "Vec::is_empty")]`, so a legacy answer with no capability is byte-identical to one that omits the field.
3. The browser sends a `terminal-e2ee-hello` carrying `{terminalId, ecdhPublicKey, signature}` over the `terminal` data channel.
4. The dispatcher handles `"terminal-e2ee-hello"` only when the offer proposed `e2ee` and no session is active yet (`apps/agent/src/lib.rs` around line 1194 and 1199; `accept_hello` dispatch at `apps/agent/src/lib.rs:1215`). It calls `E2eeSession::accept_hello(&identity, &session_id, &hello, &peer_signing_public_key_raw)`.
5. `accept_hello` (`apps/agent/src/e2ee.rs`) does three things, in order:
   - **Step 1 — verify the peer's Ed25519 signature.** Compute `canonical_key_binding(hello.ecdh_public_key)` and verify `hello.signature` against `peer_signing_public_key_raw` (the raw 32-byte Ed25519 key decoded from the offer's `userSigningPublicKey`). On failure it returns `E2eeError::BindingNotVerified` *before* any key derivation.
   - **Step 2 — derive the session key.** Generate an ephemeral P-256 key, extract the peer point from its SPKI, and derive the session key via `EncryptionManager::derive(my_private, peer_point, WS1_TERMINAL_INFO, session_id)` — i.e. ECDH → HKDF-SHA256 over the session id as salt → AES-256-GCM.
   - **Step 3 — sign the agent's binding.** Sign `canonical_key_binding(my_spki)` with the agent identity and build the `terminal-e2ee-ack`.
6. On success the session is stored in the shared `RwLock<Option<E2eeSession>>` (`apps/agent/src/lib.rs`, `RwLock` declared at :1154, session stored at :1223). The write lock is dropped *before* the ack is sent down the frame channel, so the ack marker drains through `pump_frame` and flips `armed = true` only after the session exists. On any error from `accept_hello` no session is stored and no ack is produced — the terminal stays on the plaintext path.
7. **Activation barrier (`pump_frame`, `apps/agent/src/lib.rs:915`).** `TerminalData` is encrypted only when `armed` is true *and* a session exists. Frames drained before the `E2EEAck` marker stay plaintext (the ack always precedes the first ciphertext). If the pump is armed but has no session — which the dispatch in step 6 makes impossible in practice, but the branch is guarded defensively — the frame is dropped, never plaintext. On musl (no desktop) the same terminal path applies the same rule.

## Fail-closed table

| # | Point | When the check fails | Effect |
|---|-------|----------------------|--------|
| 1 | `E2eeSession::accept_hello` — peer binding signature does not verify | `BindingNotVerified` returned before deriving | No session stored, no ack sent; terminal stays on the plaintext path |
| 2 | `accept_hello` — `ecdhPublicKey` is not valid SPKI / not an uncompressed point | `raw_point_from_spki_b64` → `MalformedFrame` / `Encoding` | Negotiation aborts; no session, no ack; plaintext only |
| 3 | `EncryptionManager::decrypt` — frame `len <= IV_BYTES + TAG_BYTES` | rejected (`MalformedFrame`) | No plaintext released; the frame is dropped |
| 4 | `EncryptionManager::decrypt` — AES-GCM tag fails | `E2eeError::Crypto` | Tampered/truncated ciphertext is dropped, never rendered |
| 5 | Pump armed but no session | `pump_frame` drops the frame | Fail-closed, never plaintext |
| 6 | Offer omits `e2ee` (or a legacy agent advertises no capability) | `negotiated_capabilities` is empty, so `negotiated` is false | No hello/ack flow is entered; the session runs on the plaintext path |

`verify_offer_identity` (`apps/agent/src/lib.rs:876`, the H3 gate) is an **admission gate for every session mode**. Its exactly one production call site is `apps/agent/src/lib.rs:1049`, placed **before** the `match mode` dispatch (see the ADR-41 comment at `apps/agent/src/lib.rs:1039-1048`), so terminal, desktop, and files offers all pass through it before the answer SDP is sent. It requires an `IdentityProof`, a `userSigningPublicKey`, an SDP-fingerprint match, and a valid `role="offerer"` signature over the canonical proof message; a failure bails out of `run_one_session` before `rtc::answer_offer` (`apps/agent/src/rtc.rs:758`, called at `apps/agent/src/lib.rs:1117`), so no answer SDP is ever produced and no PTY is spawned.

## Token-storage decision

The decision is to **keep `localStorage`** for the access and refresh tokens, for this reason: the signaling upgrade is a WebSocket session, and the platform's WebSocket flow (`packages/webrtc-core/src/transport.ts`, `WebSocketTransport`) authenticates that upgrade by minting a short-lived ticket over an `Authorization: Bearer` HTTP request, then passing that ticket as a `?ticket=` query parameter on the `wss://` URL. The browser WebSocket API cannot set a header on the initial handshake, so the access token must be in JavaScript-readable storage to mint the ticket — an HttpOnly cookie would be invisible to the JS that performs the upgrade. The adapter is `LocalStorageTokenAdapter` in `apps/web/src/services/token-storage.ts`, keyed on `remote.accessToken` / `remote.refreshToken`, and the same adapter is used by the REST client in `apps/web/src/stores/auth.ts` (`restore`, `login`) for the HTTP calls that refresh and re-mint the ticket.

Accepted residual risk: an XSS in the SPA would expose those tokens. The same week (WS5, Task 8) adds a strict Content-Security-Policy and security headers to the SPA via `apps/web/public/_headers`, which is now shipped in this branch (strict CSP, HSTS, nosniff, Referrer-Policy, Permissions-Policy) and is guarded by `apps/web/src/__tests__/headers.test.ts`. The trust model rests on the CSP and the short ticket lifetime: a stolen access token expires quickly, and the ticket is single-use and short-lived; the refresh token is the longer-lived secret and remains the highest-value XSS target. Closing that gap would require a non-HttpOnly mechanism that the WebSocket-upgrade constraint currently forbids, which is why Phase 5 keeps `localStorage` and defers a cookie/`SameSite`-based approach to a future workstream that can redesign the upgrade flow.

## What is NOT encrypted

This shipment applies to the terminal data channel only. Three classes of data are deliberately out of the application-layer confidentiality scope:

- **File transfer is not application-layer confidentiality-protected.** Per spec §4.3 (an owner-approved boundary in `docs/superpowers/specs/2026-10-05-phase5-zero-trust-e2ee-design.md`), file payloads are not routed through `EncryptionManager`. The documented reason is throughput: Week 11 drove a 50 MiB transfer to 10.94 MB/s on a 2-vCPU CI runner by optimizing the Rust build and batching ACKs, and adding AES-GCM to that path spends CPU on the exact bottleneck the team just resolved. File transfer still traverses the same DTLS session whose peer is verified in WS2 (spec §3.2 / H3), so peer substitution is caught at the connection level, but the payload bytes are not confidentiality-protected at the application layer by design.

- **Video media is not application-layer confidentiality-protected.** Per spec §4.2, video already runs over DTLS, and encrypting it at the application layer would break the WebCodecs pipeline built in Phase 3 (Week 8) — an architectural change well beyond Phase 5. Encrypted: terminal I/O, desktop input (pointer/keyboard), SDP/ICE signaling. Not encrypted: video streams.

- **Desktop input: confidentiality-covered, but not identity-bound.** Desktop input rides the same WS1 session key as the terminal path — the agent decrypts `desktop-input` frames through `decrypt_desktop_input` (`apps/agent/src/lib.rs:2267`), and the encryption is the same `E2eeSession` path — but it is confidentiality-only, not identity-bound. This is the **finding-C1 ruling** and it is stated explicitly:
  - Before Phase 6a the desktop path did **not** pass through `verify_offer_identity` (the H3 gate): the `SessionMode::Desktop` arm returned into `run_desktop_session` upstream of the then-terminal-only gate call. **ADR-41 (2026-10-07) closed this** — see the note below. Owner-ruled Week 13 (spec §3.2): H3 gates "verify the client's key/fingerprint **before spawning a PTY**", and desktop sessions spawn no PTY. Concretely, `accept_hello` only checks the hello signature against the key the offer carried (`peer_signing_public_key_raw` decoded from the offer's `userSigningPublicKey`); it does not independently confirm that the offerer's identity was verified at the connection level.
  - The consequence is that the desktop path defends against a passive observer or relay on the data channel, but gives no active-MITM protection at the signaling layer: a signaling server that substitutes the offer's signing key would still be accepted by `accept_hello`, because the binding is checked against the key the (tampered) offer carried, not against a separately-verified identity.
  - The desktop-input gate (`allow_input`, ADR-29: CLI `--allow-input` / env `AGENT_ALLOW_INPUT`, default **closed/false**) is CLOSED this week, so there is no live input-forwarding exploit path while the identity gap exists.
  - **C1 closed (Phase 6a, 2026-10-07):** ADR-41 hoisted `verify_offer_identity` to a single admission gate that runs before the mode dispatch in `run_one_session`, so the desktop and files paths now run the same verification the terminal path always ran; an offer without a valid proof bails with no answer of any kind. The E2E suite pins the desktop and files refusals (`desktop.e2e.test.ts`, `files.e2e.test.ts`). The paragraph above describes the state before that change; see `docs/superpowers/specs/2026-10-06-phase6a-interactive-desktop-design.md` §3 (ADR-41).

The residual risk also carries the WS2 TOFU boundary: the trust model verifies an offer against the signing key learned from `GET /api/agents` (server-sourced, never trusted from the client), but does not defend against a signaling server that swaps the identity keys themselves in the database. That is the documented Phase 5 boundary (spec §8: H6 is closed with a keypair, not a full PKI). See the sibling note `docs/security/2026-10-07-ws1-e2ee.md` for the browser-side framing and `docs/security/2026-10-05-ws2-peer-identity.md` for the WS2 threat model.
