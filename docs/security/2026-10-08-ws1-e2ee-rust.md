# WS1 Terminal E2EE — Rust Agent Peer and Cross-Language Proof

**Date:** 2026-10-08
**Scope:** Documents the Rust agent-side crypto peer shipped for WS1 terminal E2EE in Week 16, the shared vector file consumed by both language test suites, the negotiated capability path, the fail-closed behavior, the token-storage decision, and the scope boundary for data that is not confidentiality-protected.

## Deliverables

This document covers the Week 16 (WS1 part 2) Rust-side shipment: a Rust peer that runs the same key schedule as the browser so a terminal data channel carries confidential data end to end between the browser and a live agent.

1. **Rust `EncryptionManager` over `ring`** (`apps/agent/src/e2ee.rs`): ECDH P-256 → HKDF-SHA256 → AES-GCM-256, the same key schedule the browser uses (`packages/crypto/src/encrypt.ts`, `packages/crypto/src/session-key.ts`).

2. **Byte-identical constants:**
   - `IV_BYTES = 12`, `TAG_BYTES = 16` (`apps/agent/src/e2ee.rs`).
   - `WS1_KEY_VERSION = "ponter-ws1-v1"` and `WS1_TERMINAL_INFO = "ponter-ws1-terminal-v1"`, matching `packages/shared/src/types/e2ee.ts`.
   - The canonical binding string is `canonical_key_binding(spki) = "{WS1_KEY_VERSION}\necdhPublicKey={spki-base64}"` (the `WS1_KEY_VERSION` constant; the browser's `canonicalKeyBinding` in `packages/shared/src/types/e2ee.ts`). The browser signs and checks this exact string, and the agent both verify it and sign its own copy in `accept_hello`.

3. **P-256 SPKI interop.** `P256_SPKI_PREFIX` (a 26-byte DER prefix in `apps/agent/src/e2ee.rs`) matches the browser's `exportPublicKeySpki` output, so an SPKI base64 produced by either side decodes on the other. `spki_from_raw_point` encodes a 65-byte uncompressed point; `raw_point_from_spki_b64` decodes it back and returns `MalformedFrame` for a non-uncompressed point. The Rust test `p256_public_point_spki_matches_js_export` asserts the round-trip and the fixed base64 value.

4. **Ciphertext framing.** Every frame is `[12-byte IV][AES-GCM ciphertext ‖ 16-byte tag]`, with a fresh random IV per frame (`SystemRandom`). `decrypt` rejects any frame whose length is `<= IV_BYTES + TAG_BYTES` (i.e. one with no room for a tag) before touching the nonce, and returns `E2eeError::Crypto` on a tag failure.

5. **Shared test vectors.** Both suites consume the same file — `packages/crypto/test/vectors/e2ee-vectors.json`. The Vitest suite (`packages/crypto/test/encrypt.test.ts`) and the Rust tests (path via `concat!(env!("CARGO_MANIFEST_DIR"), "/../../packages/crypto/test/vectors/e2ee-vectors.json")` in `apps/agent/src/e2ee.rs`) all read this file. The Rust tests assert:
   - HKDF-SHA256 against the RFC 5869 A.1 known-answer vector (`hkdf_matches_rfc5869_a1_vector`).
   - AES-256-GCM known-answer vector, including the framed decrypt round-trip (`aes_gcm_matches_kat_vector`).
   - The P-256 SPKI export matches the JS export byte-for-byte (`p256_public_point_spki_matches_js_export`).
   - ECDH agreement between two ephemeral keys (`ecdh_two_ephemeral_keys_agree`).
   - `EncryptionManager` encrypt→decrypt round-trip and reject-on-tamper (`encryption_manager_round_trips_and_rejects_tamper`).
   - `accept_hello` round-trip, including the browser-side re-derivation check (`accept_hello_derives_and_round_trips`).
   - A mis-signed hello is rejected with `BindingNotVerified` (`a_mis_signed_hello_is_rejected_and_yields_no_session`).

## Negotiation flow

The agent never starts this negotiation; it only echoes a capability the offer proposed. The gating constant is `E2EE_CAPABILITY = "e2ee"` (`apps/agent/src/rtc.rs`).

1. The browser's offer carries `capabilities: [..., "e2ee"]` — only when it holds an ECDH key (`packages/shared/src/types/e2ee.ts`).
2. The agent answers with `capabilities: ["e2ee"]` (echoed), via `send_desktop_answer` / the terminal `answer_offer` path. The field on the wire is `SignalAnswer.capabilities` (`apps/agent/src/signal.rs`), with `#[serde(default, skip_serializing_if = "Vec::is_empty")]`, so a legacy answer with no capability is byte-identical to one that omits the field.
3. The browser sends a `terminal-e2ee-hello` carrying `{terminalId, ecdhPublicKey, signature}` over the `terminal` data channel.
4. The dispatcher handles `"terminal-e2ee-hello"` only when the offer proposed `e2ee` and no session is active yet (`apps/agent/src/main.rs` around line 1042 and 1104; `accept_hello` dispatch). It calls `E2eeSession::accept_hello(&identity, &session_id, &hello, &peer_signing_public_key_raw)`.
5. `accept_hello` (`apps/agent/src/e2ee.rs`) does three things, in order:
   - **Step 1 — verify the peer's Ed25519 signature.** Compute `canonical_key_binding(hello.ecdh_public_key)` and verify `hello.signature` against `peer_signing_public_key_raw` (the raw 32-byte Ed25519 key decoded from the offer's `userSigningPublicKey`). On failure it returns `E2eeError::BindingNotVerified` *before* any key derivation.
   - **Step 2 — derive the session key.** Generate an ephemeral P-256 key, extract the peer point from its SPKI, and derive the session key via `EncryptionManager::derive(my_private, peer_point, WS1_TERMINAL_INFO, session_id)` — i.e. ECDH → HKDF-SHA256 over the session id as salt → AES-256-GCM.
   - **Step 3 — sign the agent's binding.** Sign `canonical_key_binding(my_spki)` with the agent identity and build the `terminal-e2ee-ack`.
6. On success the session is stored in the shared `RwLock<Option<E2eeSession>>` (`apps/agent/src/main.rs` around line 1064). The write lock is dropped *before* the ack is sent down the frame channel, so the ack marker drains through `pump_frame` and flips `armed = true` only after the session exists. On any error from `accept_hello` no session is stored and no ack is produced — the terminal stays on the plaintext path.
7. **Activation barrier (`pump_frame`, `apps/agent/src/main.rs` around line 826).** `TerminalData` is encrypted only when `armed` is true *and* a session exists. Frames drained before the `E2EEAck` marker stay plaintext (the ack always precedes the first ciphertext). If the pump is armed but has no session — which the dispatch in step 6 makes impossible in practice, but the branch is guarded defensively — the frame is dropped, never plaintext. On musl (no desktop) the same terminal path applies the same rule.

## Fail-closed table

| # | Point | When the check fails | Effect |
|---|-------|----------------------|--------|
| 1 | `E2eeSession::accept_hello` — peer binding signature does not verify | `BindingNotVerified` returned before deriving | No session stored, no ack sent; terminal stays on the plaintext path |
| 2 | `accept_hello` — `ecdhPublicKey` is not valid SPKI / not an uncompressed point | `raw_point_from_spki_b64` → `MalformedFrame` / `Encoding` | Negotiation aborts; no session, no ack; plaintext only |
| 3 | `EncryptionManager::decrypt` — frame `len <= IV_BYTES + TAG_BYTES` | rejected (`MalformedFrame`) | No plaintext released; the frame is dropped |
| 4 | `EncryptionManager::decrypt` — AES-GCM tag fails | `E2eeError::Crypto` | Tampered/truncated ciphertext is dropped, never rendered |
| 5 | Pump armed but no session | `pump_frame` drops the frame | Fail-closed, never plaintext |
| 6 | Offer omits `e2ee` (or a legacy agent advertises no capability) | `negotiated_capabilities` is empty, so `negotiated` is false | No hello/ack flow is entered; the session runs on the plaintext path |

`verify_offer_identity` (`apps/agent/src/main.rs` around line 787, the H3 gate) runs on the **terminal** path before the answer SDP is sent. It requires an `IdentityProof`, a `userSigningPublicKey`, an SDP-fingerprint match, and a valid `role="offerer"` signature over the canonical proof message; a failure bails out of the session before `rtc::answer_offer` is called, so no answer SDP is ever produced and no PTY is spawned.

## Token-storage decision

The decision is to **keep `localStorage`** for the access and refresh tokens, for this reason: the signaling upgrade is a WebSocket session, and the platform's WebSocket flow (`packages/webrtc-core/src/transport.ts`, `WebSocketTransport`) authenticates that upgrade by minting a short-lived ticket over an `Authorization: Bearer` HTTP request, then passing that ticket as a `?ticket=` query parameter on the `wss://` URL. The browser WebSocket API cannot set a header on the initial handshake, so the access token must be in JavaScript-readable storage to mint the ticket — an HttpOnly cookie would be invisible to the JS that performs the upgrade. The adapter is `LocalStorageTokenAdapter` in `apps/web/src/services/token-storage.ts`, keyed on `remote.accessToken` / `remote.refreshToken`, and the same adapter is used by the REST client in `apps/web/src/stores/auth.ts` (`restore`, `login`) for the HTTP calls that refresh and re-mint the ticket.

Accepted residual risk: an XSS in the SPA would expose those tokens. For Phase 5 this is accepted with a mitigation in progress — the same week (WS5, Task 8) adds a strict Content-Security-Policy and security headers to the SPA via `apps/web/public/_headers`; this file is not in the current branch yet (it is FE-owned), so it is described as the intended hardening, not a shipped state. The trust model rests on the CSP and the short ticket lifetime: a stolen access token expires quickly, and the ticket is single-use and short-lived; the refresh token is the longer-lived secret and remains the highest-value XSS target. Closing that gap would require a non-HttpOnly mechanism that the WebSocket-upgrade constraint currently forbids, which is why Phase 5 keeps `localStorage` and defers a cookie/`SameSite`-based approach to a future workstream that can redesign the upgrade flow.

## What is NOT encrypted

This shipment applies to the terminal data channel only. Three classes of data are deliberately out of the application-layer confidentiality scope:

- **File transfer is not application-layer confidentiality-protected.** Per spec §4.3 (an owner-approved boundary in `docs/superpowers/specs/2026-10-05-phase5-zero-trust-e2ee-design.md`), file payloads are not routed through `EncryptionManager`. The documented reason is throughput: Week 11 drove a 50 MiB transfer to 10.94 MB/s on a 2-vCPU CI runner by optimizing the Rust build and batching ACKs, and adding AES-GCM to that path spends CPU on the exact bottleneck the team just resolved. File transfer still traverses the same DTLS session whose peer is verified in WS2 (spec §3.2 / H3), so peer substitution is caught at the connection level, but the payload bytes are not confidentiality-protected at the application layer by design.

- **Video media is not application-layer confidentiality-protected.** Per spec §4.2, video already runs over DTLS, and encrypting it at the application layer would break the WebCodecs pipeline built in Phase 3 (Week 8) — an architectural change well beyond Phase 5. Encrypted: terminal I/O, desktop input (pointer/keyboard), SDP/ICE signaling. Not encrypted: video streams.

- **Desktop input: confidentiality-covered, but not identity-bound.** Desktop input rides the same WS1 session key as the terminal path — the agent decrypts `desktop-input` frames through `decrypt_desktop_input` (`apps/agent/src/main.rs` around line 2299), and the encryption is the same `E2eeSession` path — but it is confidentiality-only, not identity-bound. This is the **finding-C1 ruling** and it is stated explicitly:
  - The desktop path does **not** pass through `verify_offer_identity` (the H3 gate). In `main.rs` the `SessionMode::Desktop` arm returns into `run_desktop_session` at line 971, upstream of the terminal-only `verify_offer_identity` call at line 1025, which only runs in the `SessionMode::Terminal` arm. Owner-ruled Week 13 (spec §3.2): H3 gates "verify the client's key/fingerprint **before spawning a PTY**", and desktop sessions spawn no PTY. Concretely, `accept_hello` only checks the hello signature against the key the offer carried (`peer_signing_public_key_raw` decoded from the offer's `userSigningPublicKey`); it does not independently confirm that the offerer's identity was verified at the connection level.
  - The consequence is that the desktop path defends against a passive observer or relay on the data channel, but gives no active-MITM protection at the signaling layer: a signaling server that substitutes the offer's signing key would still be accepted by `accept_hello`, because the binding is checked against the key the (tampered) offer carried, not against a separately-verified identity.
  - The desktop-input gate (`allow_input`, ADR-29: CLI `--allow-input` / env `AGENT_ALLOW_INPUT`, default **closed/false**) is CLOSED this week, so there is no live input-forwarding exploit path while the identity gap exists.
  - **Mandatory carry-forward:** extend the identity verification performed by `verify_offer_identity` (or an equivalent check) to the desktop path before Phase 6 opens the input-forwarding gate.

The residual risk also carries the WS2 TOFU boundary: the trust model verifies an offer against the signing key learned from `GET /api/agents` (server-sourced, never trusted from the client), but does not defend against a signaling server that swaps the identity keys themselves in the database. That is the documented Phase 5 boundary (spec §8: H6 is closed with a keypair, not a full PKI). See the sibling note `docs/security/2026-10-07-ws1-e2ee.md` for the browser-side framing and `docs/security/2026-10-05-ws2-peer-identity.md` for the WS2 threat model.
